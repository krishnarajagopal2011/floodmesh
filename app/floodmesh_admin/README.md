# FloodMesh Admin (Android)

Super-admin tool that registers FloodMesh LoRa units (ESP32-S3) over Bluetooth
LE as `civilian`, `relay` or `responder`. It implements the FMREG v1 protocol
in [`docs/ble-provisioning-protocol.md`](../../docs/ble-provisioning-protocol.md).
That document is the contract. Change it first, then this app and the firmware.

- Package / applicationId: `org.floodmesh.admin`, label "FloodMesh Admin"
- minSdk 24 (Android 7.0), because `flutter_secure_storage` and
  `shared_preferences_android` require it. targetSdk is the Flutter default.

**Why not `flutter_blue_plus`:** its current (2.x) licence requires a paid
commercial licence for any for-profit use, and it sends licence telemetry at
build time. `universal_ble` is BSD-3 and does the same job here. It also
handles the Android 12+ `BLUETOOTH_SCAN`/`BLUETOOTH_CONNECT` and Android ≤ 11
location runtime permissions, so `permission_handler` isn't needed.

## Build

```sh
cd app/floodmesh_admin
flutter pub get
flutter analyze
flutter test
flutter build apk --release      # -> build/app/outputs/flutter-apk/app-release.apk
```

The Android SDK is needed only for `flutter build apk`. `flutter analyze` and
`flutter test` run without it.

**Signing.** Without any setup, CI signs the release APK with the runner's
**debug key**, which is different on every build. An APK from one build then
can't be installed over another: you must uninstall first, and uninstalling
**deletes the stored admin identity** (export a backup first, see below).

To get the same key on every build (recommended before real use), create a
keystore once on your PC and add it as repository secrets:

```bash
keytool -genkeypair -v -keystore fm-release.jks -alias floodmesh \
        -keyalg RSA -keysize 2048 -validity 10000
base64 -w0 fm-release.jks > fm-release.jks.b64     # macOS: base64 -i fm-release.jks
```

GitHub → repository **Settings → Secrets and variables → Actions → New
repository secret**:

| Secret | Value |
|---|---|
| `FM_ANDROID_KEYSTORE_B64` | contents of `fm-release.jks.b64` |
| `FM_KEYSTORE_PASSWORD` | the keystore password |
| `FM_KEY_ALIAS` | `floodmesh` |
| `FM_KEY_PASSWORD` | the key password |

`android/app/build.gradle.kts` uses that key whenever `FM_KEYSTORE_PATH` is
set (the workflow sets it from the secret) and falls back to the debug key
otherwise. Keep `fm-release.jks` safe and **never commit it**: anyone with it
can build an "update" that installs over the admin app.

## Install (sideload)

1. Copy `app-release.apk` to the phone (USB, download from the CI artifact, etc.).
2. Open it. Android asks you to allow installs from that source (Settings →
   *Install unknown apps* → allow for your file manager/browser).
3. Install. Play Protect may warn about an unknown developer. Choose
   *Install anyway*.

## How to use

### 1. First run: create the admin identity
1. Open the app and choose a passphrase (at least 8 characters). Type it twice.
2. The app generates a P-256 key pair and encrypts the private key with your
   passphrase (key generation takes a few seconds).
3. It shows the **admin public key** (130 hex chars) and its **fingerprint**
   (16 hex chars). Tap **Copy public key**. Either compile it into the firmware
   as `FM_ADMIN_PUBKEY_HEX` (`-D FM_ADMIN_PUBKEY_HEX="04..."`), or install it
   on each unit with **Install admin key** (see step 4).
4. Go to **Admin key (key icon) → Export encrypted backup** and store the text
   somewhere safe.

On a second phone, choose **Import a backup instead**, then paste the text and
the passphrase.

### 2. Every launch: unlock
Enter the passphrase. The private key is decrypted into memory only. The lock
icon on the scan screen forgets it again.

### 3. Put the unit in provisioning mode
Hold **`#`** while powering the unit on (or while pressing RST). Bench
alternative: type `prov` on the serial console. The OLED shows
`PROVISIONING`, the call sign and a **6-digit PIN**. The unit leaves this mode
after 5 minutes without a connection, after 5 wrong PINs, or on reboot.

### 4. Scan and connect
1. Tap **Scan for units**. The first time, allow *Nearby devices* (Android 12+)
   or *Location* (Android 11 and older).
2. Units appear as `FM-XXXXX` with signal strength. Tap one.
3. Enter the PIN shown on the unit's screen. It is kept for this session.
4. The device screen shows call sign, role chip (grey civilian / blue relay /
   orange responder), firmware and board, expiry with countdown, admin key
   status and fingerprint, and unit time. A **red** admin line means the unit
   trusts a *different* admin key. Role changes from this phone will then fail.

### 5. Actions
- **Install admin key**: shown only if the unit has no admin key yet.
  Trust-on-first-use; only a factory reset on the unit removes it.
- **Make responder**: pick a duration: **10 days** (default), **1 day** or
  **10 min test**. The unit generates a fresh responder key, and the app then
  signs and stores its certificate (`set_cert`) automatically. Both steps must
  succeed. The success banner says "Certificate stored".
- **Make relay**: no expiry.
- **Make civilian (revoke)**: deletes any responder key/certificate on the unit.
- **Done (reboot unit)**: the unit reboots into normal mode.

Each command shows a green (success) or red (error) banner, then re-reads the
unit's INFO. A wrong PIN clears the stored PIN and asks again.

### 6. History
The clock icon lists registrations done from this phone (call sign, role,
expiry, time). **Copy as CSV** copies
`time_utc,call_sign,role,exp_unix,exp_utc,cert`.

## Security notes

- **Passphrase:** the admin private key is encrypted with AES-256-GCM, using a key
  from PBKDF2-HMAC-SHA256 (200 000 iterations, random 16-byte salt). The public
  key is authenticated as AAD. Salt, nonce, ciphertext and public key are stored in
  `flutter_secure_storage`. There is no recovery if the passphrase is lost.
  Use a long one: anyone with the backup text can try passphrases offline.
- **Backup:** the exported text is base64 of the same encrypted JSON. Without a
  backup, uninstalling the app or resetting the identity loses the key. Units
  that trust that key then need a factory reset (hold SOS + `0` at power-on
  for 10 s) or a reflash with a new `FM_ADMIN_PUBKEY_HEX`.
- **Reset admin identity** deletes the key permanently (two confirmations).
- **Debug-signed APK:** anyone with the (public, well-known) Android debug keystore
  could build an "update" that Android would accept over this install. Fine for
  a prototype, not for production.
- The PIN only proves you can see the unit's screen. The admin ECDSA signature is
  what authorises a role change (protocol §4, §8).

## Interop notes for the firmware

- `nonce` is used **as the 32-char hex string exactly as it appears in INFO**
  (not decoded to bytes), both in `auth` (`nonce + "|" + op`) and in `FMREG1`.
- The app re-reads INFO immediately **before every command**, so each command
  uses the current nonce. After `set_role responder` it re-reads INFO before
  `set_cert`.
- `now`/`exp` are JSON integers. `exp = now + duration` with durations 864000 /
  86400 / 600 s. `exp = now + 864000` is exactly the allowed maximum.
- `devPub` for `FMCERT1` comes from the `set_role` response (INFO `devPub` as
  a fallback), lowercased. The app checks it against INFO's `devPub`.
- MTU 517 is requested but not required. Commands are at most ~270 bytes, and
  Android does a long (prepared) write when the value exceeds MTU-3. If a RESP
  notification is truncated or not valid JSON, the app reads RESP instead.
  The same happens after 3 s with no notification. So the firmware must keep
  the last response readable on RESP.
- Scan uses Android *legacy* advertising PDUs (`legacy: true`), which fits ESP32
  NimBLE defaults. It filters on the 128-bit service UUID in the advertisement.
  Flags (3) + 128-bit UUID (18) + name `FM-XXXXX` (10) is exactly 31 bytes; if
  the name doesn't fit, putting it in the scan response is fine.

## Verification record

- `flutter analyze`: no issues. `flutter test`: all tests pass (Flutter 3.47.5).
- Tests include the **RFC 6979 A.2.5 P-256/SHA-256 vector** (public key and
  deterministic signature for "sample" match byte-for-byte), HMAC `auth`
  vectors computed with Python `hmac`/`hashlib`, a PBKDF2-HMAC-SHA256 vector,
  on-curve checks, and encrypt/decrypt with wrong-passphrase failure.
- One-off cross-check (run manually on 2026-09-23, not part of the test suite):
  5 fresh key pairs from the app code signed an `FMREG1` and an `FMCERT1`
  message each. All 10 raw r‖s signatures verified with Python
  `cryptography` 50.0.1 (`ec.ECDSA(hashes.SHA256())`, SECP256R1, public key
  via `from_encoded_point`), and the fingerprints matched `sha256(pub)[:16]`.
